# REA (Reverse Engineer Anything)

- 분석 범위: rea GitHub repo의 `main` 커밋 `7375ab6`와 npm `rea-agents` 6.4.0/6.5.0
- 본문의 소스 경로/라인은 해당 `main` 기준. 버전별 동작 차이는 필요한 곳에 표시
- 소스/문서 대조에 기반한 분석이며 REA 서버와 각 엔진의 실제 실행은 미검증

---

## 0. 요약

REA는 기존 리버스 엔지니어링 엔진과 자체 정적 분석 기능을 LLM 에이전트에 제공하는 **로컬 stdio MCP 서버 겸 CLI**. 네이티브 디컴파일은 Hopper/Ghidra/IDA 등 외부 엔진을 활용하고 JS/.NET 등 일부 분석은 자체 처리. 결과는 Evidence 레코드로 정규화하며 에이전트가 이를 해석해 다음 분석이나 구현을 결정.

1. 외부 엔진과 자체 분석 기능을 공통 도구로 제공. LLM 에이전트가 결과를 해석하고 후속 작업을 결정
2. Evidence에 출처/분석 조건/한계/미확인 항목을 남겨 후속 분석과 검증에 재사용
3. 큰 분석 결과는 보관하고 필요한 요약과 페이지만 전달
4. **샌드박스가 아니다.** 런타임 관찰은 사용자 권한으로 대상을 실행하며 호출 승인은 클라이언트에서 통제

주요 기능은 대상/세션 관리, 정적 분석, 런타임 관찰, Evidence 관리, 비교/검증. 전체 도구 목록과 버전별 개수는 4.3의 접기 영역에 정리.

## 2. 리버스 엔지니어링?

소스 없이 배포된 결과물의 구조와 동작을 파악하는 작업. REA는 정적 분석과 런타임 관찰을 함께 연결한다.

### 2.1 정의

완성된 결과물에서 출발해 설계와 동작 원리를 알아내는 작업. 소프트웨어에서는 실행 파일/바이트코드/배포된 JS 번들 등이 분석 대상.

쉽게 말하면:

- 소스 코드 없이 실행 파일만 보고 "이 버튼을 누르면 어떤 함수가 호출되고 어떤 파일이나 서버에 무엇을 보내는지" 알아내기
- 문서가 없는 파일 포맷/네트워크 프로토콜의 규칙을 실제 데이터와 통신을 관찰해 정리하기
- 악성코드 샘플이 감염 후 어떤 조건에서 무엇을 하는지 밝혀내기

### 2.2 정적 분석과 동적 분석

| 구분 | 방법 | 대표 도구 | 한계 | REA에서 해당하는 도구군 |
| --- | --- | --- | --- | --- |
| 정적 분석 | 실행하지 않고 파일 자체를 디스어셈블/디컴파일 | Ghidra, IDA Pro, Hopper, JADX, JEB, objdump/Rizin | 실행 중에 복호화되거나 동적으로 로딩되는 코드는 놓친다 | 엔진 연동 도구와 자체 파서 |
| 동적 분석 | 실행하면서 관찰(디버거, 로그, 패킷 캡처, 프로토콜 관찰) | 엔진 내장 디버거(Ghidra/IDA/JEB), adb, TShark | 격리된 실행 환경 필요. 실제로 실행된 경로만 보인다 | 런타임 관찰/Frida/adb 도구 |

실무에서는 둘을 병행. 디스어셈블/디컴파일 등 세부 용어는 부록 B 참고.

악성코드 분석/취약점 연구/비공개 포맷의 상호운용성 확보/레거시 유지보수 등에 활용. REA를 사용할 때도 먼저 “어떤 동작을 확인할 것인가”를 정하고 필요한 분석 경로를 선택한다.

단계 번호는 참조용.

| 3. 연결/전송 | 클라이언트가 `npx rea-agents@<버전> mcp`를 자식 프로세스로 실행, stdio JSON-RPC. initialize 때 짧은 서버 instructions 전달(대상 유무별 2종 + 신뢰 불가 콘텐츠 지침). 호출을 실제로 보낼지는 클라이언트가 결정 | 도구가 안 보이거나 클라이언트가 차단하면 `doctor`/`setup --dry-run` 복구 절차. 보이면 진단 반복 없이 바로 대상으로 | 없음(setup/doctor는 CLI) | 없음 |

### 3.2 요청 흐름의 역할 분담

- **에이전트**: 질문을 분석 작업으로 나누고 결과를 해석. 확인하지 못한 부분은 후속 호출이나 미확인 항목으로 기록
- **REA 서버**: 입력 검증, 세션/프로세스 관리, 엔진 호출, Evidence 정규화와 결과 크기 제어
- **분석 엔진/자체 파서**: 디컴파일/메타데이터 추출/런타임 관찰 등 실제 분석

서버 내부 처리 단계는 4.2, 엔진 연결 방식은 5.2 참조. 같은 흐름을 따르더라도 대상에 따라 진입 도구와 엔진 준비 방식이 달라진다.

### 3.3 대상 라우팅과 엔진 바인딩 분기

**skill의 대상별 첫 도구 라우팅**(`SKILL.md`)

- ASAR/JS: `analyze_javascript_application`
- APK 코드: `inspect_android_package`
- .NET: `inspect_managed_artifact`
- 네이티브: `open_binary` 후 필요한 분석 도구 등

대상별로 어떤 엔진을 연결하는지는 5장에 정리. `open_binary`로 깊은 네이티브 분석 엔진을 고정하는 경로와 경로/엔드포인트를 직접 받는 도구를 구분해야 한다.

**엔진 바인딩 규칙**(`open_binary`, 분석 대상 `main` 기준)

- `provider_id`: 특정 엔진 ID 또는 `auto`. 환경변수 `REA_ANALYSIS_PROVIDER`로도 지정
- `auto`는 사용 가능 후보가 정확히 1개일 때만 선택. 2개 이상이면 `ambiguous` 오류, 0개면 미바인딩
- 성공하면 엔진/버전/선택 근거/분석 프로파일 **고정**
- 런타임 실패가 나도 다른 엔진으로 **자동 전환하지 않는다**("no failure fallback")
- 필요한 엔진이 없으면 `binary_session`의 `tool_availability`에서 원인과 해결 방법 확인

## 4. MCP 서버 내부

### 4.1 stdio 통신

클라이언트가 REA를 자식 프로세스로 실행하고 stdin/stdout으로 JSON-RPC 요청/응답을 교환. 로그는 stderr로 출력하며 클라이언트와 REA 사이에 수신 포트를 열지 않는다(`src/main.ts`, MCP Transports).

등록 예시. setup은 실행한 패키지 버전으로 고정해 기록(`docs/installation.md`).

    ```json
    { "mcpServers": { "rea": { "command": "npx", "args": ["-y", "rea-agents@6.4.0", "mcp"] } } }
    ```

REA가 IDA/JEB에 연결할 때는 별도의 MCP **클라이언트** 역할. 이 구간은 엔진 설정에 따라 HTTP 또는 stdio를 사용하며 REA 자체의 클라이언트 연결과 구분(5.2).

로컬 통신이어도 실행 권한은 제한되지 않는다. REA는 클라이언트와 같은 OS 사용자 권한으로 동작하므로 런타임 분석의 격리와 호출 승인은 별도 관리(6장).

### 4.2 요청 처리 파이프라인

<center><img width="1200" src="https://github.com/user-attachments/assets/ebe5cb43-7f32-48cb-a4c1-100330108f9a"></center>
<center><em style="color:gray;">요청 처리: 입력 검증 → 세션 진입 제어 → 분석 실행 → 대상/실행 일치 검사 → Evidence 생성/보관 → 응답 크기 검사. 실패 시 오류 응답 반환.</em></center><br>

그림은 3장 그림의 "REA MCP 서버" 박스를 펼친 것(`main` `7375ab6`).

`tools/call` 요청 하나는 다음 순서로 처리된다.

1. **입력 검증**: 도구 핸들러 조회 후 입력 스키마로 인자 검사. 검증 실패 시 실행 중단.
2. **세션 진입 제어**: 진행 중인 대상 전환(open/close)이 끝날 때까지 대기.
3. **분석 실행**:
    - 경로 직접 입력 도구(JS/Electron, Android, .NET 등): 해당 서비스에서 실행
    - 바인딩 도구(`analyze_function`, `xrefs` 등): 활성 대상/엔진 확인 후 호출. 첫 호출 시 엔진 시작
    - 대상/엔진/프로파일 일치 시 분석 스냅샷 재사용
4. **Evidence 생성/보관**: 결과 정규화 → 내용 해시 ID 부여 → 세션에 보관. 같은 ID의 레코드는 중복 처리.
5. **응답 구성**: 크기 상한 초과 시 Evidence 참조와 이어 읽기 요청으로 대체(4.5). 분석 대상 콘텐츠에는 신뢰 불가 표시 추가(6.3).

출처: repo `docs/mcp-contracts.md`, `src/server/`.

### 4.5 Evidence 보관과 결과 크기 제어

<center><em style="color:gray;">Evidence 레코드, 세션 기록, 결과 크기 제어와 종료 흐름: 분석 도구 호출 → Evidence 레코드 → 세션 Evidence ledger → 전체 레코드/요약 Evidence/응답 예산 초과 → 에이전트 → 페이지 조회 → export_evidence_bundle → close_binary → 보관 레코드 삭제</em></center><br>

REA의 핵심 설계는 "결과 = 증거 레코드"(`docs/mcp-contracts.md` Tool results).

- 성공 시 text와 `structuredContent` 양쪽에 같은 Evidence 레코드를 동일한 형식으로 반환.
- 공통 응답 스키마는 strict(정의되지 않은 최상위 필드 거부). 주요 필드:

| 필드 | 내용 |
| --- | --- |
| `evidence_id` | 레코드 내용 해시(`ev_...`). 같은 ID로 중복 제거하며 다른 도구 입력에 참조로 전달 가능 |
| `subject` | 분석 대상(이름, SHA-256, 형식, 아키텍처) |
| `provider`, `analysis_profile` | 결과를 낸 엔진과 버전/설정 |
| `operation`, `parameters` | 실행한 작업과 인자 |
| `raw_result`, `normalized_result` | 엔진 원본 결과와 엔진 무관 정규화 결과 |
| `confidence` | `observed`(관찰) / `derived`(유도) / `inferred`(추론) |
| `limitations`, `relationship_coverage` | 분석 한계와 호출 관계 수집 범위(`complete`/`partial`/`unknown`) |
| `evidence_links` | 연결된 다른 Evidence의 ID |

도구별 `normalized_result` 안의 값. 공통 응답의 최상위 필드와 구분(`docs/mcp-contracts.md`):

| 값 | 위치/내용 |
| --- | --- |
| `coverage` | 예: 아티팩트 인벤토리의 `coverage.scope`(`root`/`container-entries`), `coverage.status`(`complete`/`unknown`) |
| `facet_availability` | 함수 종합 분석 결과의 항목별 상태 맵. pseudocode, assembly, callers 등 분석 항목의 관찰 여부 |
| `residual_unknowns` | 추적/조사 도구 결과의 남은 미확인 항목 |

- 원칙: **관찰(observation)/유도(derivation)/추론(inference)/미확인(unknown)을 구분**.
    - "빈 호출 목록 + 커버리지 partial"은 "호출이 없다"는 뜻이 아니다.
    - `compare_functions`의 `changed`는 텍스트 차이일 뿐 동작 차이가 아니다.
- 무결성 검사는 기본이 fail-closed. 해시 불일치 시 중단. `integrity_policy=record-and-continue`를 명시할 때만 격리 후 계속.

**결과 크기 제어(컨텍스트 사용량 관리)**

| 수단 | 내용 |
| --- | --- |
| `detail: "summary"` | `analyze_javascript_application`, `inspect_binary_layout`, `inspect_artifact` 등. 완전한 Evidence는 세션에 저장, 요약 Evidence만 반환 |
| `inspect_analysis_view` | 보관된 Evidence의 요약, 섹션/모듈 하나, 안정적인 페이지(`next_offset`) 조회 |
| 응답 크기 초과 | 결과가 응답 크기 상한(기본 10 MiB)을 넘으면 자르지 않고 보관 Evidence 참조와 이어 읽기 요청(`continuation`)으로 대체(4.1) |
| 탐색 | `get_evidence_bundle`의 `detail:"summary"` + 필터(operation, target_sha256, procedure_address 등). payload 없이 ID만 반환 |
| 페이지네이션 | `list_unknowns`의 `offset`/`limit`/`next_offset` |
| 스키마 축소 | `REA_MCP_INPUT_SCHEMA_PROFILE=compact`: 각 도구 입력 스키마를 13,312바이트 이내로 축소(Moonshot/Kimi의 크기 제한 대응). `REA_MCP_OUTPUT_SCHEMA_PROFILE=off`: 도구 목록에서 outputSchema 생략(서버 쪽 검증은 유지) |
| 예시 축소 | 입력 스키마 예시에 완전한 Evidence 대신 `evidence_id` 참조만 기재. 예시도 모델 컨텍스트를 소비하기 때문 |

### 4.6 세션 관리

- **연결 1개 = 세션 1개**. `open_binary`로 대상과 엔진 바인딩을 결정(3.3 바인딩 규칙).
- 대상이 바뀔 때마다 엔진 기동 전에 `analysis_run.run_id` 할당. 엔진 프로세스 계보(PID, 부모, 프로세스 그룹, 자식)를 스냅샷으로 기록.
- 세션 안에 Evidence ledger와 미확인 항목 목록 보관. 대상 전환에도 유지.
    - 조회: `get_evidence_bundle`(`detail:"summary"` + 필터)
    - 내보내기: `export_evidence_bundle`로 파일에 원자적 기록
    - 불러오기: `import_evidence_bundle`
    - 분석 스냅샷은 바이너리 동일성, 엔진, 프로파일이 정확히 일치할 때만 재사용
- `close_binary`는 진행 중인 작업 정리와 엔진 종료 후 **세션 보관 레코드를 삭제**. 필요한 Evidence는 닫기 전에 export 필요.
- JS/Electron, 웹, .NET 같은 "target-free" 도구는 `open_binary` 없이 경로나 엔드포인트를 직접 입력받는다.
    - 경로 직접 입력 도구도 대상 전환 대기/취소 확인 수행. 활성 대상/엔진 바인딩 검사와 스냅샷 캐시는 생략.

## 5. 엔진과 연결 방식

### 5.1 엔진 요약

| 엔진 | 대상 | 비고 |
| --- | --- | --- |
| **Ghidra** | 네이티브 바이너리(x86, ARM 등) | 미국 NSA가 공개한 무료 오픈소스 |
| **IDA Pro** | 네이티브 바이너리 | Hex-Rays 상용 제품, 업계 표준 |
| **Hopper** | 네이티브 바이너리(macOS/iOS 중심)[^1] | 상용. REA 설치 중에 승인하면 자동 설치 가능 |
| **JADX** | Android APK(dex→Java) | 무료 오픈소스. REA는 headless 모드로 사용 |
| **JEB** | Android, 네이티브(WebAssembly/EVM 등도 지원)[^2] | 상용(PNF Software). JEB가 MCP 서버를 띄우고 REA가 거기에 연결 |
| Apktool | APK 리소스 | 보조 도구 |
| Binwalk / Unblob | 펌웨어 추출 | REA 기준 Linux 전용[^3] |
| objdump / Rizin | 오프라인 네이티브 검사 | 경량 대안 |

> 상용 도구(IDA, Hopper, JEB)는 라이선스 직접 확보 필요(REA README 명시). REA는 도구 라이선스/키/활성화 권한을 제공하지 않는다. 체험판/데모도 벤더 약관(사용자 수, 기능, 자동화, 출력 공유 제한)을 따른다.[^4]
> 

[^1]: Hopper는 Mach-O(macOS/iOS)에 강점이 있지만 x86/x64(Windows 바이너리 포함)와 ARM도 다룬다(hopperapp.com). 실행 플랫폼은 macOS/Linux. REA의 Windows 실험적 지원은 Ghidra 연동 기준이며 Hopper의 Windows 지원을 뜻하지 않는다.
[^2]: JEB는 Android(Dalvik)와 네이티브(x86/ARM/MIPS/RISC-V) 외에 WebAssembly, Ethereum EVM, Nvidia SASS, S7 PLC도 지원(pnfsoftware.com).
[^3]: "Linux"는 REA 연동 기준(README: Linux에서 자동 실행, procps 호환 `ps` 필요). Unblob 자체는 macOS도 지원(unblob GitHub).
[^4]: 표에 없는 REA 보조 연동 도구: adb(Android 실기기/에뮬레이터), TShark(패킷 캡처), sigrok-cli(로직 신호), pwntools(Linux x64 ELF/EVM/크래시), WABT(WebAssembly), Chrome 계열 브라우저(웹사이트 분석). 엔진별 상세는 표의 엔진만 설명(부록 A).

### 5.3 브리지와 headless의 차이

**브리지**는 REA 요청을 엔진 내부 API 호출로 바꾸는 연결 코드. Hopper에서는 내부 Python 스레드가 요청을 처리하고 Ghidra에서는 Java 브리지가 분석된 프로그램에 접근한다.

**Headless**는 GUI 없이 분석 기능을 실행하는 방식. Ghidra의 `analyzeHeadless`로 임시 프로젝트에 대상을 임포트한 뒤 브리지를 실행하면 사용자 GUI 작업과 분리해 질의를 처리할 수 있다. 작업 종료 후 임시 프로젝트를 정리(`SECURITY.md`, `src/ghidra/GhidraLauncher.ts`).

두 개념은 별개. REA는 headless로 기동한 엔진에도 브리지를 두며 IDA/JEB처럼 외부 MCP 서버에 연결하는 경로도 사용한다.

### 5.4 엔진 선택 가이드

| 상황 | 추천 |
| --- | --- |
| 무료로 네이티브 바이너리를 깊게 분석 | Ghidra |
| 조직에 IDA 라이선스가 있고 디컴파일 품질이 최우선 | IDA Pro (REA headless 모드 또는 attached) |
| macOS/iOS 바이너리, 저예산 상용 도구 | Hopper |
| Android APK의 Java 코드 | JADX (무료) → 난독화 대응/대화형 리팩터링이 필요하면 JEB |
| Android 리소스/매니페스트/리패키징 | Apktool (JADX와 병행) |
| APK 안의 네이티브 라이브러리(.so) | JADX/Apktool로 추출 후 Ghidra 또는 IDA |
| 펌웨어 이미지 | Binwalk 또는 Unblob으로 추출(Linux) → 나온 바이너리를 Ghidra/IDA로 |
| GUI 엔진 없이 빠른 정적 확인, CI/경량 환경 | objdump 또는 Rizin |

오픈소스 조합 예: Ghidra + JADX + Apktool + Binwalk/Unblob + objdump/Rizin. 네이티브/Android/펌웨어 분석에 활용 가능하며 실제 지원 범위는 대상 형식과 각 엔진의 기능에 따라 결정.

| 승인 | REA는 권한 부여나 호출별 승인 플래그를 요구하지 않는다. 승인 UI는 MCP 클라이언트 몫. setup만 계획을 보여 주고 확인 요청(6.1) | `docs/mcp-contracts.md` Request scope |

| 공급망 | Hopper 설치는 HTTPS 공식 출처 + 체크섬(SHA-1, 손상 검사 수준). `sudo`는 호출하지 않고 `pkexec` 사용. README에 이름이 비슷한 repo와 복제 README를 주의하라는 경고 | `SECURITY.md`, README |

### 6.1 호출 승인은 에이전트 클라이언트 몫

**MCP의 역할 분담**

| 주체 | 역할 |
| --- | --- |
| MCP 서버 | 도구 목록 제공, 요청 검증, 실행과 결과 반환 |
| 모델 | 어떤 도구를 부를지 선택 |
| 클라이언트(Claude Code, Cursor 등) | 그 호출을 **실제로 보낼지 결정**. 사람에게 "이 도구를 실행할까요?"라고 묻는 창도 클라이언트가 표시 |

- **REA가 하지 않는 것**: REA 서버는 호출마다 사용자에게 묻거나 승인 토큰을 요구하지 않는다.
    - 별도 승인 UI 없이 유효한 요청 실행("REA does not require permission grants or per-call approval flags... MCP clients control their own confirmation UI", `docs/mcp-contracts.md:472-474`)
    - 설정 변경을 수행하는 `setup` CLI는 별도로 계획 표시/확인 요청

### 6.2 annotation은 힌트일 뿐

- REA는 도구마다 효과를 선언하고(`src/contracts/toolEffects.ts:55`) 여기서 MCP 힌트를 기계적으로 계산(`:714-737`).
- `destructiveHint` = true 조건(하나라도 해당 시): 데이터 폐기 가능(`mayDiscardData`), REA가 소유하지 않은 코드 실행(`executesForeignCode`), Android 기기 변경(`mutatesDevice`)
- 필자가 `toolEffects.ts`를 정적으로 파싱한 결과 `main` 207개 중 31개가 `destructiveHint: true`(예: `capture_process_scenario`, `load_frida_script`, `gdb_console`, `cutter_command`, `install_adb_package`, `close_binary`, `set_comment`).
- 하지만 MCP 사양상 annotation은 서버가 스스로 붙이는 설명이라 클라이언트가 믿거나 따를 의무가 없다(문서도 "hints, not authorization controls"라고 명시, `docs/mcp-contracts.md:476-477`). MCP 사양 2025-11-25 Tools: "clients MUST consider tool annotations to be untrusted unless they come from trusted servers".
- 힌트가 위험을 전부 담지도 않는다. 예: `start_frida_session`은 프로세스를 spawn하고 대상을 바꿀 수 있지만(`mutatesTarget`, `launchesProcess`) 위 세 조건에 해당하지 않아 `destructiveHint`는 false(`toolEffects.ts:204-210`).

실제 호출 허용/승인/차단은 클라이언트의 권한 규칙으로 설정. REA 프로세스의 실행 권한과 격리는 별도로 관리한다.

<details class="post-disclosure" markdown="1">
<summary>Claude Code 권한 모드와 설정 예시</summary>

**Claude Code에서 통제하는 방법**(일반론, 출처: Claude Code permissions, Claude Code MCP)

- **권한 규칙**: settings 파일의 `permissions.allow / ask / deny`.
    - MCP 도구 이름 형식은 `mcp__<서버 이름>__<도구 이름>`. setup이 등록하는 서버 이름이 `rea`이므로 `mcp__rea__capture_process_scenario`처럼 표기.
    - `mcp__rea` 또는 `mcp__rea__*`는 REA 도구 전체에 매칭
    - 평가 순서는 **deny → ask → allow**이고 먼저 매칭된 규칙이 결정. 좁은 allow로 넓은 deny를 무효화할 수 없다.
- **권한 모드**: `defaultMode`로 시작 모드 지정.

| 모드 | 동작 |
| --- | --- |
| `default` | 기본 권한 정책에 따라 필요한 호출에 승인 요청 |
| `acceptEdits` | 파일 편집 승인 자동 허용. 모든 MCP 호출을 허용하는 모드는 아니다 |
| `plan` | 분석/계획 중심. 변경 작업 제한 |
| `auto` | 분류기가 검토 |
| `dontAsk` | 승인이 필요한 호출은 거부. 승인 불필요 작업과 사전 허용 작업은 실행 가능 |
| `bypassPermissions` | 질문 생략. 격리된 컨테이너/VM에서만 쓰라고 경고 |

- **MCP 인자 단위 제한은 settings로 불가**: settings 파일의 `mcp__` 규칙에 괄호 인자를 붙이면 무시된다. 인자까지 걸러야 하면 `--disallowedTools` 또는 PreToolUse hook 사용. hook의 차단은 allow 규칙보다 우선.
- **항상 묻게 만드는 서버 측 표시**: 서버가 `tools/list`에 `_meta["anthropic/requiresUserInteraction"]: true`를 넣으면 Claude Code는 auto/bypass 모드에서도 매번 질문.
    - REA 소스(`main` `src/`)에는 이 표시가 없다.
    - Claude Code 문서에서 `readOnlyHint`/`destructiveHint`를 승인 판단에 쓴다는 설명은 미확인.
- **설정 예시**(필자 제안. 실제 적용 전 조직 정책에 맞게 조정): REA는 분석 전용 프로필(`CLAUDE_CONFIG_DIR=~/.claude-rea`, 6장 등록 범위)에서만 쓰고 그 프로필의 settings에 아래처럼 둔다. `"mcp__rea__*"`를 allow에 넣으면 프로세스 실행/기기 변경 도구까지 자동 승인되므로 피한다.

```json
{
  "permissions": {
    "defaultMode": "default",
    "allow": [
      "mcp__rea__binary_session", "mcp__rea__open_binary", "mcp__rea__binary_overview",
      "mcp__rea__analyze_function", "mcp__rea__search_strings", "mcp__rea__inspect_analysis_view"
    ],
    "ask": [
      "mcp__rea__capture_process_scenario", "mcp__rea__observe_native_calls",
      "mcp__rea__capture_browser_scenario", "mcp__rea__capture_electron_scenario",
      "mcp__rea__start_frida_session", "mcp__rea__load_frida_script",
      "mcp__rea__install_adb_package", "mcp__rea__push_adb_file", "mcp__rea__export_evidence_bundle"
    ],
    "deny": [
      "mcp__rea__cutter_command", "mcp__rea__gdb_console",
      "mcp__rea__execute_rizin_command", "mcp__rea__rizin_debug_command"
    ]
  }
}
```

</details>

보안 함의:

- 클라이언트 권한 설정은 **REA 도구 호출**만 통제.
- REA 프로세스 자체는 사용자 권한으로 실행. 따라서 신뢰할 수 없는 대상의 런타임 캡처/Frida/디버거 도구는 권한 규칙과 별개로 격리 VM/컨테이너에서 실행해야 한다.
- 분석 결과 안의 문자열이 "이 명령을 실행하라"고 유도하는 프롬프트 인젝션(6.3)에 대해서도 프로세스 실행/기기 변경 도구를 `ask`/`deny`로 두는 것이 최종 통제 수단.

### 6.3 프롬프트 인젝션

- 분석 대상의 문자열/심볼/의사코드/웹 페이지 텍스트/로그는 공격자가 통제할 수 있다.
    - "이 명령을 실행하라", "필요한 헬퍼를 내려받아라" 같은 문자열을 심어 두면 에이전트가 지시로 받아들일 위험이 있다.
    - REA 문서가 이 시나리오를 직접 예로 듦(`docs/mcp-contracts.md` Untrusted target content).
- REA의 대응:
    - 결과 `_meta`에 `untrusted_content` 표시. 도구 계약 단위(`returnsTargetContent`, 기본 on)로 선언하고 성공/실패 모두 표시
    - 서버 지침으로 따르지 말라고 안내. 실행/설치/다운로드/전송 요구는 인젝션 시도로 보고하라고 안내
    - 호스트나 훅이 이 표시를 보고 이후 프로세스 실행/기기 변경 도구에 승인을 요구할 수 있도록 지원
    - 구현 위치(`main`): `src/server/toolResultEncoding.ts:26`, `src/server/createServer.ts:147`
    - 버전: 6.4.0 패키지에는 이 표시가 없다. 6.5.0 `dist/server/createServer.js`, `dist/server/toolResultEncoding.js`에서 확인. 6.4.0 이하 버전에 고정된 등록에서는 이 표시에 기대면 안 된다.
- 실무 권고:
    - 분석 세션에서는 셸 실행/네트워크/기기 변경 도구에 수동 승인 설정(Claude Code 설정 예시는 6.2)
    - REA 등록 범위를 전용 프로필이나 컨테이너로 한정
    - 에이전트를 만드는 쪽도 외부 문서나 툴 결과를 지시로 취급하지 않도록 provenance 표시와 승인 게이트를 설계

## 7. 한계와 비판

1차 출처(프로젝트 스스로 밝힌 것):

- 디컴파일, 재구성, AI 분석 결과는 불완전하거나 틀릴 수 있다(`DISCLAIMER.md`). 자체 디컴파일 기술은 없으며 품질은 엔진에 좌우.
- 커버리지 미확인은 "없음"이 아니다(`docs/mcp-contracts.md`).
    - 비교 결과 `changed`도 텍스트 차이일 뿐
    - 정적 일치가 런타임 동작 동일을 뜻하지 않는다
- 난독화된 managed 코드 비교, 간접 호출, 아키텍처 확장은 로드맵 과제(`docs/roadmap.md`).
- Windows: Ghidra 실험적 지원(읽기 전용), PTY 캡처 미지원.
- 대형 바이너리: Ghidra 콜드 스타트가 클라이언트 60초 기한을 넘길 수 있다.
- **토큰 절감 효과는 미입증**(프로젝트 실험 기록 `experiments/analysis-efficiency/README.md:49`):
    - summary/선택 뷰로 응답 바이트는 크게 감소
    - 실제 Codex 시행에서는 모델 입력 토큰이 오히려 늘거나 시간이 엇갈려 "model-token savings are not claimed"라고 기록
    - 작은 함수에서는 선택 응답 4번이 전체 함수 분석 결과 1번보다 바이트가 많았던 사례도 존재
- 스키마 크기: 전체 카탈로그가 일부 클라이언트(Kimi/Moonshot, WorkBuddy, pi-web-ui, strict-depth 클라이언트)의 크기/깊이 제한에 걸려 compact 프로파일을 별도로 둔다(`docs/mcp-contracts.md:675-721`).

디컴파일/재구성 결과의 독립 정량 평가는 미확인. 실제 도입에서는 대상과 질문을 고정하고 정확도/시간/모델 비용을 함께 비교할 필요가 있다.

## 8. REA MCP 설계 분석

### 8.1 실사용 시 고려할 점

**평가 방법**

프로젝트는 스키마와 추가 호출/재시도까지 포함한 전체 작업 비용을 측정하도록 명시(`AGENTS.md` Performance).

도입 평가에서도 같은 대상/질문으로 성공률과 모델 토큰/경과 시간을 반복 측정. 콜드/웜 실행을 구분하고 도구 선택 오류와 재시도도 포함. 분석 결과는 `compare_*`/`verify_reconstruction` 등으로 별도 검증한다.

**비용**

| 항목 | 내용 | 출처 |
| --- | --- | --- |
| 엔진 라이선스 | Ghidra/JADX 등 무료 도구와 IDA/Hopper/JEB 등 상용 도구를 구분. 상용 라이선스는 별도 확보 | README License, 5.1 |
| 모델 토큰 | 도구 결과를 모델 입력에 포함하면 토큰 사용량 발생. 과금 방식은 모델/클라이언트에 따라 차이 | README FAQ |
| 도구 카탈로그 | 전체 목록 제공과 모델 컨텍스트 적재는 별개. 실제 비용은 클라이언트의 도구 검색/지연 로딩 방식에 따라 차이 | 4.3, 8.2 |
| 시간 | 엔진 콜드 스타트. Ghidra 시작 시간이 클라이언트 타임아웃을 초과할 가능성 | 7 |

**운영 주의**

- 등록 범위: setup은 사용자 전역에 등록. 분석 전용 프로필이나 별도 계정/컨테이너로 한정(6장 등록 범위, 8.4).
- 버전 고정: 등록은 설치 버전에 고정. 6.4.0에 고정된 등록은 `untrusted_content` 표시와 Frida 등 추가 도구가 없다. 업그레이드는 명시 행위로 다시 setup.
- 타임아웃: 큰 바이너리는 `REA_GHIDRA_STARTUP_TIMEOUT_MS`/`REA_HOPPER_STARTUP_TIMEOUT_MS` 연장과 클라이언트 호출 타임아웃 조정 필요.
- 격리: 런타임 캡처/Frida/디버거는 격리 VM/컨테이너에서만.
- 데이터 경계: 원격 모델을 사용하면 결과가 외부 모델 제공사로 전송될 수 있으므로 조직의 데이터 정책을 사전에 확인.
- Evidence 보존: `close_binary`가 세션 기록을 삭제하므로 필요한 Evidence는 먼저 `export_evidence_bundle`.
- 설치 출처: 이름이 비슷한 repo/zip 배포에 주의(README:28-33).

### 8.2 MCP 설계 사례로서의 강점과 한계

엔진 연결, Evidence 관리, 권한 분리를 중심으로 구현과 문서의 설계 선택을 살펴본다.

| 설계 | REA의 구현 | 적용할 점과 한계 |
| --- | --- | --- |
| 엔진 중립 인터페이스 | 공통 도구 이름 뒤에서 엔진별 어댑터 호출 | 엔진 교체와 도구 사용을 분리. 지원 기능 차이는 가용성과 coverage로 전달(5.2) |
| Evidence 계약 | ID/출처/분석 조건/신뢰도/한계를 결과에 포함 | 빈 결과와 수집 실패를 구분하고 후속 도구가 같은 결과를 참조. 결과의 정확성 자체를 보장하지는 않는다(4.5) |
| 결과 크기 제어 | 전체 결과를 보관하고 summary/페이지/continuation 제공 | 모델에 필요한 부분만 전달하고 나머지는 후속 조회로 제공(4.5) |
| 엔진 고정과 오류 처리 | 대상별 엔진을 고정하고 실패 시 자동 전환 금지 | 재시도로 분석 출처가 바뀌는 문제 방지. 오류에는 원인과 복구 방법 제공(3.3) |
| 권한과 신뢰 경계 표시 | effects에서 annotation 계산, 분석 대상 콘텐츠에 `untrusted_content` 표시 | 효과 선언과 실제 동작을 대조. annotation/출처 표시는 승인이나 샌드박스를 대체하지 않는다(6장) |
| 지침과 도구 분리 | 서버 instructions, MCP prompt, 버전이 맞는 skill 제공 | 상세 절차를 필요할 때 읽도록 분리. skill이 없는 클라이언트와도 동작 차이 점검(4.4) |

출처: `docs/mcp-contracts.md`, `docs/tool-design.md`, `src/domain/evidence.ts`, `src/contracts/toolEffects.ts`.

도입 시 남는 문제는 세 가지.

- **큰 도구 카탈로그**: 207개 목록은 일부 클라이언트의 스키마 크기/깊이 제한에 걸린다. compact 프로파일은 이 제한에 대응하지만 도구 선택 모호성이나 모델 컨텍스트 비용을 모두 해결하지는 않는다
- **장시간 엔진 작업**: 엔진 시작 시간과 클라이언트 타임아웃을 함께 맞춰야 한다. progress 알림만으로 호출 종료를 막을 수 있는 것은 아니다
- **사용자 권한 실행**: 실제 실행 위험을 클라이언트 승인과 격리 환경에서 통제해야 한다

단일 엔진 MCP와 비교할 때 REA의 차이는 도구 개수보다 **여러 엔진의 결과를 같은 Evidence/세션/검증 절차로 다루는 점**. IDA/JEB 경로에서는 기존 엔진 MCP의 클라이언트로 동작하므로 단순한 대체 제품 관계도 아니다(5.2).

### 8.3 소프트웨어를 배포하는 쪽의 보안 함의

배포된 바이너리/APK/JS 번들은 사용자가 확보해 분석할 수 있다. REA는 문자열 검색/디컴파일/IPC 추적/source map 복원 등을 에이전트 작업 흐름으로 연결한다.

| 배포물에서 확인할 것 | 대응 방향 |
| --- | --- |
| 비밀값과 클라이언트 측 권한 검사 | 장기 비밀값과 서버 자원에 대한 권한 판단은 서버에서 관리 |
| source map/디버그 정보/불필요한 코드 | 운영 배포에 포함할 범위를 정하고 비공개 보관이 필요한 파일의 접근 제한 |
| Electron IPC/모바일 앱 경계 | 발신자/입력 검증과 서버 측 권한 확인. 난독화/무결성 신호만으로 보호된다고 가정하지 않는다 |

출처: OWASP MASVS/MASWE-0004, Electron Security/ASAR Integrity, OWASP WSTG-INFO-05.

방어 측에서도 같은 도구로 배포물을 사전 점검할 수 있다. 다만 분석 대상 실행은 격리 환경에서 수행하고 원격 모델을 사용한다면 분석 결과의 외부 전송 범위를 확인해야 한다.

### 8.4 클린룸과 EULA

- REA 문서 자체의 클린룸 조건(`docs/installation.md`):
    - 구현 환경이 REA, 대상, 분석 결과를 **읽거나 가져올 수 없도록 별도 계정이나 컨테이너로 강제**해야 한다.
    - 같은 OS 계정의 프로필 분리만으로는 접근 차단 불가.
    - 분석 결과에 접근 가능한 구현 환경은 이 문서의 분리 조건을 충족하지 않는다.
- 분석 결과나 소스와 비슷한 산출물을 얻었다고 원 프로그램이나 산출물에 대한 권리가 생기지 않는다(`DISCLAIMER.md`).
    - 상용 SW의 EULA 역공학 금지 조항, 국가별 상호운용성 예외 범위는 법무 확인 필요
    - 이 문서는 법적 판단을 하지 않는다
- 상용 엔진의 체험판/데모도 자동화와 출력 공유 제한을 포함한 벤더 약관을 따른다(README).

## 부록 A. 엔진별 운영 참고

### A.1 Ghidra

REA가 설치된 Ghidra를 headless로 기동. 큰 바이너리는 `REA_GHIDRA_STARTUP_TIMEOUT_MS`와 클라이언트 호출 타임아웃을 함께 조정. Windows 연동은 실험적 지원(REA README, Ghidra provider 문서).

### A.2 IDA Pro

실행 중 GUI의 DB에 붙는 attached와 별도 워커를 쓰는 headless 경로를 구분. REA는 IDA 라이선스/설치/업그레이드를 관리하지 않는다. 연결하려는 MCP와 IDA 버전의 호환성 확인(`docs/ida-provider.md`).

### A.3 Hopper

macOS/Linux에서 사용. 첫 실행 라이선스 대화상자를 완료해야 CLI/MCP에서 사용할 수 있다. 큰 바이너리는 `REA_HOPPER_STARTUP_TIMEOUT_MS` 조정(REA README).

### A.4 JADX

APK의 DEX 코드를 Java 형태로 분석. REA는 headless JADX와 JDK를 사용하며 APK 내 네이티브 라이브러리는 별도의 네이티브 엔진으로 분석(REA README).

### A.5 JEB

사용자가 JEB MCP 서버를 준비하고 REA가 `REA_JEB_MCP_URL`로 접속. 라이선스와 자동화 조건은 사용자 책임(REA README).

### A.6 Apktool

Android 리소스/매니페스트 디코딩에 사용. Java 코드 분석은 JADX/JEB와 역할 분담(REA Android 문서).

### A.7 Binwalk / Unblob

펌웨어의 내장 파일/영역 추출. REA 연동은 Linux 기준이며 추출한 바이너리의 깊은 분석은 별도 엔진에서 수행(REA README).

### A.8 objdump / Rizin

명시적으로 호출하는 오프라인 검사 도구. Hopper/Ghidra/IDA 실패 시 자동 전환되는 엔진 후보가 아니다. 직접 명령 뒤 세션 재개 조건은 3.1 참조(`src/composition/binary.ts`, 도구 계약).

## 부록 B. 용어 정리

- **디스어셈블(disassemble)**: 기계어를 어셈블리 명령어로 해석. 코드/데이터 구분이나 명령어 경계 판단 오류 가능.
- **디컴파일(decompile)**: 기계어/바이트코드에서 C/Java 같은 고수준 의사코드를 복원. 읽기 쉽지만 변수명/타입/구조는 추정치라 틀릴 수 있다.
    - Dalvik/Java 바이트코드: 정보가 많이 남아 디컴파일이 비교적 정확
    - 네이티브 코드: 더 어렵다
- **정적 분석(static)**: 실행하지 않고 파일 자체를 분석(Ghidra, IDA, JADX 등). 대상을 직접 실행하지 않지만 파서 취약점 위험은 존재. 런타임 복호화/동적 로딩은 관찰 범위 밖.
- **동적 분석(dynamic)**: 실제로 실행하며 관찰(디버거, adb 로그, 패킷 캡처 등). 실제 동작을 확인할 수 있지만 실행 환경 격리 필요.
- **headless**: GUI 없이 CLI/API로 엔진을 실행하는 모드. 자동화/CI/LLM 에이전트 연동(REA)의 기반(5.3).
- **stdio transport**: MCP 클라이언트가 서버를 자식 프로세스로 띄우고 stdin/stdout 파이프로 JSON-RPC를 주고받는 방식(4.1).
- **Evidence 레코드**: REA 도구 결과의 공통 응답 구조. 내용 해시 `evidence_id`, 출처, 신뢰도, 한계 등 16개 필드(4.5).
- **세션 기록(EvidenceLedger)**: 연결 하나에 하나씩 있는 Evidence 보관소. `close_binary` 때 삭제(4.6).
- **엔진 바인딩**: `open_binary`가 대상 하나에 깊은 분석 엔진 하나를 고정하는 것. 실패해도 자동 전환하지 않는다(3.3).
- **target-free(경로 직접) 도구**: `open_binary` 없이 경로/엔드포인트를 직접 받는 도구. 단 세션 진입 시 검사는 거친다(4.2).
- **annotation(`readOnlyHint`/`destructiveHint`)**: 서버가 도구에 붙이는 MCP 힌트. 권한 통제 수단은 아니다(6.2).
- **`untrusted_content`**: 분석 대상에서 나온 콘텐츠가 담긴 결과의 `_meta.provenance` 표시. 6.5.0에 포함(6.3).
- **클린룸 설계**: 분석 팀과 구현 팀을 분리해 독립 창작을 보이는 방식(8.4).
